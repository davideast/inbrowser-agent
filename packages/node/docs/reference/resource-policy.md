# Resource policy

Every bounded value the runtime enforces - byte caps, counts and deadlines - is
named once in `src/resource-policy.ts`. `DEFAULT_RESOURCE_POLICY` holds exactly
the constants the runtime shipped with, so a container booted without
`resources` behaved identically to one booted before the policy existed. The
policy changes where a bound is _written down_. Later changes to a default are
deliberate and listed below.

## Removed keys

`timers.channelAckMs` (5 s) has been removed. It was a peer-acknowledgement
deadline, and every site that used it failed or closed a healthy channel whose
peer, a guest or the host page, was merely busy in synchronous code; Node has no
such deadline. Its scope narrowed site by site (below) until nothing used it. An
override may still name it: `resolveResourcePolicy` validates the value as before
(a positive safe integer; otherwise `RangeError`/`ERR_OUT_OF_RANGE`, or
`TypeError`/`ERR_INVALID_ARG_TYPE` for a non-number) and then ignores it, so a boot
configuration written for an earlier runtime keeps working and the resolved policy
has no such key. `REMOVED_LIMITS` in `src/resource-policy.ts` names it. Raising it
used to tolerate longer busy periods; there is now no deadline to raise. This is
the first removed key; no earlier key was removed, so there was no precedent to
follow.

## Changed scope

These entries record how `timers.channelAckMs` lost its users before its removal.

`timers.channelAckMs` no longer applies to fork IPC. It used to close a fork
channel when the peer had not acknowledged a send, or finished a disconnect,
within 5 s. A peer that is merely busy in synchronous code does not answer, and
Node never closes a channel for that: messages queue and arrive when the peer's
event loop turns. In `next build` the export worker's channel closed this way
with `ERR_IPC_CHANNEL_CLOSED` while the main process was busy. Fork IPC now has
no deadline. Memory stays bounded by `child.ipcQueuedMessages` and
`child.ipcQueuedBytes`, counted until the peer's event loop reads each message (or delivers it, before its listeners are ready), and a send
past either throws E2BIG. Native Node buffers without that bound; the bound is a
documented divergence. A dead peer is detected by its termination: the parent's
process record stops the channel when the child exits, is killed or fails, and a
parent's exit removes its children. Overriding it no longer changed fork IPC.

Nor does it apply to worker_threads messages any more. Each `postMessage` armed a
5 s acknowledgement timer that closed the port when a thread or parent busy in
synchronous code did not read the message in time; Node never closes a port for
that. The port now has no deadline; `child.threadQueuedMessages` and
`child.threadQueuedBytes` count messages the peer has not read, and a
`postMessage` past either throws E2BIG. Termination, `terminate()` and `close()`
end the port.

Child stdin writes no longer use it either. The parent failed a write with
ETIMEDOUT when the host had not answered it within 5 s; while the host page was busy
in synchronous code that happened to healthy writes, where a native pipe write has
no deadline. The host answers every write as soon as it handles it, so the parent
now waits for that answer; the child's exit fails the rest with EPIPE, and the
existing `child.inputQueueDeliveries` and `child.inputQueueBytes` bounds still fail
a write past them with E2BIG.

Thread and child startup no longer use it. `fork()`, `spawn()` and `new Worker()`
failed with ETIMEDOUT ("Child startup timed out", "Thread startup timed out") when
the host had not answered the start request within 5 s, which a host page busy in
synchronous code caused; Node has no startup deadline. The host answers every start
request with `spawned` or an error, and its only wait, the kernel attach request,
has its own bound (`syscall.kernelRequestTimeoutMs`), so the parent now waits for
that answer.

Module publication no longer uses it either. A process failed an ES module import
with ETIMEDOUT ("Module publication timed out") when the host had not answered the
publication within 5 s, which a host page busy in synchronous code caused. The host
answers every publication, published or failed, so the process now waits for that
answer.

## How it is resolved and plumbed

1. `BrowserContainer.boot` calls `resolveResourcePolicy(overrides)`. Overrides are
   a deep partial: any subset of groups, any subset of a group's keys. Unset keys
   keep their defaults.
2. Validation follows Node's argument-validation conventions, not the runtime
   error taxonomy, because an invalid override is a caller mistake in a boot
   option rather than a limit being reached: a wrong shape or an unknown group or
   key raises `TypeError` with `code: 'ERR_INVALID_ARG_TYPE'` (a removed key,
   listed under "Removed keys", is validated and ignored instead), and a value that
   is not a positive safe integer, or exceeds a hard maximum the runtime already
   enforced, raises `RangeError` with `code: 'ERR_OUT_OF_RANGE'`. The message
   names the rejected path, for example `resources.snapshot.entries`.
3. Resolution happens before any Worker is constructed or any service worker is
   registered, so an invalid override cannot leave a partly started container.
4. The resolved policy travels on the messages that already exist: the kernel
   Worker receives it on the `ready` handshake, every process Worker on its
   `boot` message, and the service worker on `register` (and again on `discover`,
   the recovery path after a service-worker restart). Each realm installs it with
   `installResourcePolicy` before any guest code runs, and enforcement sites read
   it with `resourceLimits()`. The service worker is the exception: it serves
   several containers at once, so it keeps each container's policy in its owner
   record.
5. Three hard maxima predate the policy and are still enforced:
   `http.responseBytes` at most 64 MiB, `filesystem.descriptorReadBytes` at most
   64 MiB, `install.unzipBytes` at most 256 MiB. The context compiler limits add
   two: `modules.contextSourceBytes` at most 256 MiB and
   `modules.contextOutputBytes` at most 1 GiB, because the reply length travels in
   a signed 32-bit header word and the reply buffer reserves its maximum as
   address space.

## Budgets over streamed bodies

Preview HTTP is streamed, so two of its limits are totals rather than buffer
sizes: `preview.requestBodyBytes` and `preview.responseBytes`. Their defaults are
1 MiB and 64 MiB (the response default was 8 MiB; see Changed defaults) and the failure when one is exceeded, but they
have no hard maximum - any positive safe integer is accepted - and they are the
only limits that may be marked unbounded:

```ts
import { BrowserContainer, UNBOUNDED } from '@inbrowser/node';
const container = await BrowserContainer.boot({
  resources: { preview: { responseBytes: UNBOUNDED, requestBodyBytes: 256 * 1024 * 1024 } },
});
```

`UNBOUNDED` is `Infinity`. `resolveResourcePolicy` accepts it only for the limits
named in `UNBOUNDED_LIMITS`; for every other limit `Infinity` is still
`ERR_OUT_OF_RANGE`, because those size a buffer, a queue or a deadline. What
bounds memory for a streamed body is the in-flight window:
`preview.requestWindowBytes` and `preview.responseWindowBytes` are the most body
bytes one exchange may have posted and not yet consumed in each direction, and
they cannot be unbounded. A window below the 64 KiB transport chunk shrinks the
frame to the window. `BrowserContainer.previewStreams()` reports the peak bytes
that were in flight. See
[Preview HTTP transport](architecture.md#preview-http-transport).

A page hosting several containers shares one host realm. Host-realm helper
modules - the IndexedDB stores, install, `execArgv` parsing, output-stream
observers - read the realm accessor, so those host-side bounds follow the most
recently booted container; kernel, process-Worker and preview bounds are
per-container and exact.

## Outbound HTTP egress policy

`BootOptions` accepts optional outbound HTTP/HTTPS host controls enforced in
`src/browser-http.ts` (`httpAllowedHosts`, `httpBlockedHosts` and grouped
`httpEgress: { allowedHosts?, blockedHosts? }`):

- Patterns match exact hosts (`api.example.com`, `127.0.0.1`, `[::1]`), wildcard
  subdomains (`*.example.com`, which matches `sub.example.com` and
  `a.b.example.com` but not bare `example.com`), `*`, and optional explicit
  `:port` suffixes (`api.example.com:8443`, `*.example.com:80`). Effective ports
  default to `80` for `http:` and `443` for `https:`. Trailing-dot FQDNs
  (`api.example.com.`) normalize to `api.example.com`, and IPv4-mapped IPv6
  literals (`[::ffff:127.0.0.1]` / `[::ffff:7f00:1]`) canonicalize to dotted-quad
  IPv4 in both rule parsing and request matching (`src/resource-policy.ts:607`,
  `src/resource-policy.ts:863`).
- `blockedHosts` is evaluated before `allowedHosts` (deny overrides allow). When
  `allowedHosts` is defined, every non-matching host/port is denied; an empty
  array (`allowedHosts: []`) denies all outbound guest HTTP/HTTPS requests. When
  composed across a cross-origin `installSandboxHost` boundary,
  `intersectHttpEgressPolicies` (`src/resource-policy.ts:827`) unions `blockedHosts`
  and requires every target to match both host and client `allowedHosts` layers.
- Invalid patterns fail synchronously during `BrowserContainer.boot` with
  `EINVAL` before any Worker or service worker starts
  (`src/resource-policy.ts:742-777`, `src/index.ts:448-452`).
- Disallowed requests fail in `src/browser-http.ts:413`, `src/browser-http.ts:849`
  with `EACCES` (`UnsupportedError`, `kind: 'unsupported'`) before `fetch()` hits
  the network, and `result.url` is re-validated after `fetch()`
  (`src/browser-http.ts:440-448`), cancelling `result.body` if the final URL
  lands on a disallowed origin.
- Resolved egress rules travel on the container's boot policy carrier so guest
  processes, `child_process` children and `worker_threads` Workers inherit them
  automatically. Note that this policy governs Node's `http`/`https` adapter;
  raw `globalThis.fetch` inside a Worker remains governed by browser `connect-src`
  CSP headers (see [threat-model.md](threat-model.md)).

## Deprecated aliases

`httpResponseLimit`, `unzipLimit` and `descriptorReadLimit` remain supported
`BootOptions` and keep their own `EINVAL` validation and messages. Each maps into
the policy - `http.responseBytes`, `install.unzipBytes` and
`filesystem.descriptorReadBytes` respectively - and an explicit `resources` entry
wins when both are given. They are deprecated, not removed.

## Context compiler buffer

In experimental async-context mode each process owns a compiler Worker. The
request (source, filename and the two bounds) goes by `postMessage`; only the
reply travels through a `SharedArrayBuffer`. That buffer is growable:
`new SharedArrayBuffer(8 + 1 MiB, { maxByteLength: 8 + modules.contextOutputBytes })`.
The compiler Worker calls `grow()` (to a whole number of MiB) only when a reply
needs more, and never past the maximum. The process reads each reply through a
view created after the reply arrives, and the compiler writes through a view
created after growing, so both sides see the grown length. A reply above
`contextOutputBytes` is not written; the Worker reports its size and the process
raises `E2BIG`. The timeout, termination on timeout and non-reuse of a timed-out
compiler are unchanged.

Memory per process: before, an eagerly allocated buffer of 32 MiB plus a header
of 8 bytes; now 1 MiB plus the header at start, growing to the largest reply seen
(rounded up to a whole MiB). The policy maximum (128 MiB by default) is only the
size the engine may let the buffer grow to; this work did not measure committed
versus reserved memory for it. Nothing else sized by these limits is eager: module
sources are strings, measured when published or served.

## Fixed limits

These stay constants in their own modules. A Worker sizes a buffer from one at
boot, both peers must agree on one before either can validate a message, or the
realm that enforces it never receives a boot message - so an override could only
produce a protocol mismatch, not a smaller budget. `FIXED_LIMITS` in
`src/resource-policy.ts` names the structural ones for discoverability.

## Deliberately unbounded

Listed in [the threat model](threat-model.md): CPU and heap per guest process,
the virtual listener registry (`listen`), containers per page, total IndexedDB
footprint, and the rate of raw `globalThis.fetch` calls from guest code outside
Node's `http`/`https` adapter. `child.maxProcesses` bounds concurrent guest
Workers per container, and `filesystem.maxTotalBytes`, `filesystem.maxInodes`
and `filesystem.maxOpenDescriptors` bound the in-memory volume, while CPU and V8
heap scheduling remain owned by the browser.
